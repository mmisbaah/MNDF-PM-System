# Windows installer

The installer places one immutable, signed release under `C:\PerformanceTracker\releases`. It never embeds or fabricates database passwords, MFA keys, service credentials, TLS private keys, release-signing private keys, or organization records.

The production payload is allowlisted to the prepared standalone application, a pinned portable Node.js 24 runtime (including its license), explicitly named operational scripts, database migrations, and deployment templates. Repository metadata, source-only files, release-gate/build orchestration, build caches, test and lint helpers, local seed tools, browser checks, test output, and development dependencies are excluded. Run the release gate from the controlled release checkout before packaging; do not install the build toolchain on the application host. Unsigned rehearsal packages may retain the wider signed release script inventory for diagnostic parity; they are never production-authorized.

Production compilation uses a disposable staging copy so Authenticode signatures never modify the reviewed checkout or its provenance-bound build output. It signs all staged PowerShell helpers, regenerates the staged full-package manifest, signs that manifest with the offline-custody Ed25519 key, verifies both integrity layers, compiles the installer, signs the EXE, and removes staging even after failure.

Production compilation requires:

- a clean, provenance-recorded standalone release with an Ed25519 release-manifest signature;
- an installer version exactly matching the source-controlled `performance-tracker` version in the signed standalone package metadata;
- access to the organization-controlled Authenticode certificate private key and the separately guarded Ed25519 release-signing key/passphrase;
- the pinned Inno Setup 6.7.3 compiler whose SHA-256 fingerprint and valid Pyrsys B.V. Authenticode publisher signature are verified before use;
- the separately verified release public key and its recorded fingerprint;
- the pinned Node.js 24.19.0 executable, verified by SHA-256 and a valid OpenJS Foundation Authenticode signature before it is executed;
- a Windows SDK signing tool with an independently approved SHA-256 fingerprint and valid Microsoft Authenticode signature, plus an organization-controlled code-signing certificate;
- an Authenticode-signed final installer whose RFC 3161 timestamp certificate matches an independently approved thumbprint;
- an attended deployment administrator to provision restricted PostgreSQL roles, TLS, protected secrets, ACLs, and the dedicated non-administrator service account.

`build-installer.ps1 -AllowUnsignedRehearsal` exists only for disposable installation testing. Its output is not authorized for production distribution.

Run an unsigned package on an elevated, disposable Windows staging host with `scripts/run-installer-rehearsal.ps1`. The runner refuses the production installation root and any pre-existing target, independently checks the installer and release-key fingerprints, installs silently, verifies the installed signed manifest and full payload, exercises uninstall, and writes a versioned JSON evidence record. It confirms that protected configuration/data roots and immutable releases remain for an explicit custody decision while replaceable runtime helpers are removed. The rehearsal deliberately does not connect to a production database or authorize the unsigned package for deployment.

Change the application version only through a reviewed source commit. The builder rejects a free-form `-AppVersion` value that does not exactly match the package metadata covered by the release integrity manifest.

The default `TrustedCompilerSha256` pins the reviewed Inno Setup 6.7.3 compiler. A compiler upgrade requires a separately reviewed source change to that fingerprint; do not override it merely to make an unfamiliar binary pass. The installer build record includes the verified compiler hash and publisher subject.

Every successful build creates `<installer>.build.json` using exclusive creation. The builder refuses to replace an existing installer, record, or reserved signature path. The portable version 8 record uses adjacent safe filenames rather than build-machine paths and binds the installer hash to the source commit, release identifier, compiler identity, Windows signing-tool hash/publisher, bundled Node runtime hash/publisher, release trust key, production-helper allowlist, Authenticode signer subject/thumbprint, RFC 3161 timestamp-authority thumbprint, signing status, and UTC creation time. Production builds also create `<installer>.build.json.sig.json` with the offline-custody Ed25519 key and immediately verify it against the pinned public key. Preserve and transfer all three production artifacts together in one directory. Rehearsal records deliberately omit signing-tool and signer identity, remain unsigned, and state `productionAuthorized: false`. Console output is informational and is not a substitute for retained evidence.

Before transferring or running an installer, place the three production artifacts in a dedicated handoff directory with ACL inheritance disabled and write access limited to SYSTEM, local Administrators, and explicitly approved custodians. Launch production installations only through `scripts/install-verified-package.ps1`, supplying `-ApprovedPackageCustodians`, explicit installer, build-record, public-key, approved Node-runtime path, and the independently recorded `-ApprovedInstallerSha256`, `-ApprovedAppVersion`, `-ApprovedReleaseCommit`, `-ApprovedReleaseId`, `-ApprovedSigningCertificateThumbprint`, `-ApprovedTimestampCertificateThumbprint`, `-ApprovedSignToolSha256`, and `-ApprovedReleasePublicKeySha256`. The launcher holds non-write-sharing handles on all three artifacts throughout verification and installer execution, preventing a verified bundle from being replaced before it is consumed. Production verification rejects inherited handoff permissions or write-capable ACL entries for any unapproved identity. It also snapshots all three artifact hashes and confirms they remain unchanged after cryptographic verification. It checks the exact authorized installer digest, version, source commit and installed release identifier, EXE Authenticode signature, actual signer and timestamp authority, release tools, runtime hash and OpenJS publisher, and Ed25519 trust key against those independent approvals. These controls prevent a valid historical installer, rebuilt substitute, renamed deployment identity, mutable handoff bundle, or its signed record from authorizing its own promotion. Direct `verify-installer-package.ps1 -AllowUnsignedRehearsal` use accepts only records explicitly marked non-production and never converts or launches them as deployable artifacts.

The production launcher additionally requires independently approved SHA-256 fingerprints for `install-verified-package.ps1`, `verify-installer-package.ps1`, and `installer-package-acl.ps1`. It obtains non-write-sharing locks on all three tools before validating them and retains those locks through installer completion, so they cannot be substituted between fingerprinting and use. The same full-duration lock covers the release public key and the exact `node.exe` used for cryptographic verification, preventing approved trust inputs from being replaced after their fingerprints are checked. Their directories must also have ACL inheritance disabled, and neither the key nor runtime may grant write-capable access to an identity outside SYSTEM, local Administrators, and the explicitly approved custodians. Record post-signing tool fingerprints in the attended release approval; a repository path or filename alone is not approval.

The executed `release-signing.mjs` cryptographic helper is part of the same independently fingerprinted, full-duration locked verification-tool set. Its approved SHA-256 value must be supplied as `-ApprovedReleaseSigningHelperSha256`; approving only the PowerShell wrapper scripts is insufficient. Every component of the verification-tool, handoff-artifact, release-key, and Node-runtime paths must resolve without junctions, symbolic links, or other reparse points; redirected paths are rejected before trusted code or data is consumed. Protected directories and files must also be owned by SYSTEM, local Administrators, or an explicitly approved custodian; an unapproved owner is rejected even when no current write access rule is visible.

The attended authorizer must create a `performance-tracker-install-approval-v1` JSON record containing the approved installer hash, signer and timestamp thumbprints, version, commit, release ID, compiler, signing-tool, release-key, runtime, launcher, verifier, ACL-helper, cryptographic-helper hashes, and the complete approved package-custodian identity list. Custodians must be recorded and supplied as immutable Windows SID values, never reusable account names. Record the approval file's SHA-256 independently and supply both `-ApprovalRecordPath` and `-ApprovedApprovalRecordSha256`; the launcher locks this record with the bundle and rejects mixed values from different approvals or a widened custodian trust list.

Create this file with `scripts/new-installer-approval.ps1`; do not hand-author it. The generator uses exclusive creation, records the System Authorizer's immutable SID and UTC approval/expiry timestamps, and limits validity to 14 days. The launcher rejects missing or unknown fields, reusable approver names, non-UTC timestamps, future-dated approvals, expired approvals, and validity periods longer than 14 days. Keep the independently recorded SHA-256 outside the installer handoff directory.

Production installation also requires the signed `performance-tracker-rehearsal-acceptance-v1` `GO` record created after the attended staging rehearsal and cleanup. Supply its record, detached signature and public key together with independently recorded SHA-256 values for the record and public key. The launcher protects and locks all three artifacts, verifies the signature, requires distinct rehearsal operator and authorizer SIDs, and binds the accepted release ID, commit, installer hash and installer-approval hash to the package being launched. The rehearsal authorizer must match the installer-approval authorizer. A `NO_GO`, altered record, substituted key, mixed approval, or acceptance for another release blocks installation before the executable starts.

Before requesting elevation, run the same `scripts/install-verified-package.ps1` command with `-PreflightOnly -PreflightReportPath <new-json-path>`. This executes the launcher's complete locked ACL, fingerprint, signature, approval, acceptance, release and runtime verification path, but it does not start the installer or trigger its elevation prompt. It exclusively creates a redacted `performance-tracker-install-preflight-v1` report only after every check passes and prints its SHA-256 for independent recording. Keep `-PreflightReportPath`, remove `-PreflightOnly`, and add `-ApprovedPreflightReportSha256 <independently-recorded-hash>` for the elevated installation. The report is valid for 24 hours. The launcher protects and locks it, repeats every verification, and refuses installation unless its complete release, tool, trust-key, certificate, runtime, approval, acceptance, and redacted custodian-set fingerprints still match.

After attended host provisioning, run migrations with `apply-migrations.ps1 -EvidencePath <new-json-path> -ReleaseId <release-id>` and independently record the printed hash. Then run `new-production-installation-receipt.ps1` from an elevated deployment-administrator session. It verifies the migration evidence, installed release signature and integrity, fixed scheduled-task ownership and service identity, running task result, loopback health contract, and recursive production ACL policy. Only after every check passes does it create, sign, and immediately verify an immutable, redacted `performance-tracker-production-installation-receipt-v1`. Keep the receipt, detached signature, public receipt key, and independently recorded receipt SHA-256 as the final deployment record; keep the receipt private key outside the installation root.

Auditors and administrators can validate that final record offline with `verify-production-installation-receipt.ps1`. The verifier requires no elevation, signing private key, database URL, application credential, or production connection. Supply independently approved SHA-256 values for the verifier itself, receipt, receipt public key, Node executable, and `release-signing.mjs`, plus the expected host, release ID, and commit. It rejects redirected or mutable inputs, locks itself with all evidence and trust inputs, authenticates the OpenJS Node.js publisher, verifies the detached receipt signature and exact schema, and confirms the recorded deployment was passed, redacted, healthy, and bound to the expected release.

Create portable audit evidence with `new-installation-audit-bundle.ps1` only after the receipt passes independent verification. The command copies the receipt, detached signature, receipt public key, pinned verifier and cryptographic helper under fixed names; records the approved external Node.js 24 hash, version and OpenJS signer; creates a full SHA-256 inventory; and signs and verifies the bundle manifest with a separate audit-bundle key. The private key remains outside the bundle. Preserve the independently recorded manifest and public-key hashes during transfer. The bundle intentionally excludes Node binaries, private keys, environment files, database URLs, credentials, logs, and application data.

Before opening transferred evidence, run a separately delivered, independently fingerprinted `verify-installation-audit-bundle.ps1`. Supply the approved manifest, bundle public-key, verifier, external `release-signing.mjs`, and OpenJS Node.js hashes together with the expected host, release ID, and commit. The verifier requires every initial trust input to remain outside the bundle, locks the complete fixed file set, authenticates the manifest, rejects added, missing, changed, or redirected content, matches the recorded external runtime identity, then runs the now-authenticated enclosed receipt verifier. It requires no private key, elevation, credentials, database URL, production connection, or application data.

For accountable transfers, the sender runs `new-audit-bundle-custody-handoff.ps1` after bundle verification. It records the sender and named receiver Windows SIDs, approved transfer-method classification, deployment identity, and manifest fingerprints in a signed, secret-free handoff. The named receiver runs `confirm-audit-bundle-custody-receipt.ps1`; it authenticates the sender record, confirms the current Windows identity is the named receiver, independently verifies the transferred bundle, and creates a separately signed receipt. Preserve the handoff, both detached signatures and public keys, receiver receipt, and independently recorded fingerprints outside the bundle.

An auditor can validate the complete transfer offline with a separately delivered, independently fingerprinted `verify-audit-bundle-chain-of-custody.ps1`. It locks every input, rejects redirected evidence, authenticates the OpenJS Node.js runtime and both signatures, enforces exact versioned schemas and UTC chronology, and binds the receipt to the handoff, transfer UUID, sender and receiver SIDs, approved method, audit manifest, trust keys, host, release ID, and commit. It requires no signing private key, passphrase, credentials, database URL, production connection, or application data.

If a transfer cannot be acknowledged, an approved custodian runs `new-audit-bundle-custody-exception.ps1` while no receiver receipt exists. It creates a signed, immutable, secret-free exception using only controlled classifications: acknowledgement overdue, receiver unavailable, transfer media lost, or transfer cancelled. Overdue records cannot be issued before the configured 1–720 hour acknowledgement window expires. Receipt creation races invalidate and remove the exception, while prior receipts or exceptions are never replaced.

Uninstall removes runtime scheduled tasks but deliberately retains configuration, evidence, logs, backups, audit exports, and immutable releases. Those records require a separate authorized retention or destruction decision.
